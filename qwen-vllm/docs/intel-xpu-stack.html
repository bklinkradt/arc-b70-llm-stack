Overview

What runs where when vLLM serves Qwen3.8-27B on the Arc Pro B70, and where the MTP corruption comes from.

The short version

The MTP corruption was a known bug in the GDN convolution kernel of vllm-xpu-kernels. It was fixed upstream in August 2026, but the fix is not in the intel/llm-scaler-vllm:0.26.0-b2 image. Both the cause and the fix are confirmed on this machine, and the deployment now runs upstream vLLM v0.30.0, which includes the fix.

During an MTP verify step, the SYCL kernel causal_conv1d in vllm-xpu-kernels stores the short convolution history of each GDN layer in its own layout: one snapshot per draft position. With prefix caching on, vLLM copies that history into a new cache block each time a sequence crosses a 2048-token boundary. vLLM assumes the upstream layout: one sliding window, read at an offset of num_accepted_tokens − 1. When two or more drafts were accepted on the step that crosses a boundary, the copy picks up rows the kernel never wrote. All 48 GDN layers then continue from a damaged state, and the output decays into newline floods or gibberish without any error.

On the path where the corruption happens

One MTP step, top to bottom

This is the path a single decode step takes when MTP is on. Each step names the chapter that covers it.

  1. Scheduler (EngineCore process). It schedules each running request's last token plus up to 3 draft tokens from the previous step, and assigns cache blocks. With prefix caching, the GDN state for a request lives in a block that changes every 2048 tokens. Ch. 1, ch. 3.

  2. State copy before the step. In 'align' mode, preprocess_mamba copies the conv and SSM state from the old block to the new one when a request has crossed a boundary. The conv copy uses the upstream row-offset convention. Ch. 3.

  3. Verify forward in XPUModelRunner. The target model runs over the 4 tokens. Full-attention layers use FA2 paged attention. Each GDN layer calls forward_xpu, which on this bf16 model always ends in torch.ops._xpu_C.gdn_attention. Ch. 2.

  4. GDN kernels (SYCL). causal_conv1d reads the conv window chosen by num_accepted_tokens and writes one snapshot per spec position. The gated delta rule then updates the SSM state per token. Ch. 2, ch. 3.

  5. Rejection sampling. At temperature 0 the target's argmax decides how many drafts are kept, from 0 to 3, plus one bonus token. This count becomes num_accepted_tokens for the next step.

  6. Draft proposal. The single MTP layer (full attention only, no GDN) runs 3 times to propose the next drafts. Errors here can only lower acceptance, never corrupt output. Ch. 3.

  7. Below the Python. Each kernel launch goes through SYCL and the Unified Runtime to Level Zero and the NEO driver, then to the xe kernel driver and GuC, which schedule it on the GPU's compute engine. Copies may run on the copy engine. Ch. 4.

Primer: model, attention and tiles

A plain-language explanation of what Qwen3.8-27B computes, the two kinds of attention it uses, and how the kernels cut that work into tiles for the Arc Pro B70. Read this first if the later chapters assume too much. Unlike the rest of the guide, this chapter describes the setup that is serving now: upstream vllm/vllm-openai-xpu:v0.30.0 with MTP 3 and prefix caching on. Tile sizes and line numbers are from vllm-xpu-kernels tag 0.1.14.1 (commit 6d92b1b), the version that image ships. Its installed flash_attn_interface.py is byte-identical to the tag's.

The model in one picture

A language model reads a list of tokens and predicts the next one. Each token becomes a vector of 5120 numbers (the hidden state). That vector passes through 64 layers, and each layer adds a little more context to it. At the end, the LM head turns the final vector into a score for each of the 248,320 tokens in the vocabulary. The sampler picks one of them.

Every layer has the same two parts:

  • A mixer: the only place where a token looks at other tokens. In this model the mixer is either full attention or GDN linear attention.
  • An MLP (a feed-forward block, 5120 → 17408 → 5120): works on each token by itself. Most of the weights are here, and they are the part stored as INT4.

Qwen3.8 alternates the two mixer types in a fixed pattern: three GDN layers, then one full-attention layer, repeated 16 times.

There is also one MTP head: an extra full-attention layer that guesses the next few tokens cheaply, so the main model can check several guesses in one pass. It is on in the current docker-compose.yml, with 3 draft tokens per step. On the llm-scaler image it corrupted output (the bug in chapter 3). The v0.30.0 kernels contain the fix.

What attention does

Attention answers one question for each token: "which earlier tokens matter to me, and what do they say?" The layer makes three vectors from each token:

  • Query (q): what this token is looking for.
  • Key (k): what this token can offer, used for matching.
  • Value (v): the content this token hands over when it matches.

For the current token, the layer compares its q with the k of every earlier token (a dot product), turns those scores into weights that add up to 1 (softmax), and returns the weighted sum of the v vectors. A token can only look backwards. This is the causal rule.

Heads. The layer does this many times in parallel, each with its own smaller q, k and v. Each copy is a head, and different heads learn to follow different things. In Qwen3.8's full-attention layers:

QuantityValueMeaning
Query heads2424 separate "questions" per token
Key/value heads4Only 4 sets of k and v are stored

Query heads per KV head6Grouped-query attention (GQA): 6 query heads read the same k/v, which makes the cache 6× smaller
RoPEon 25% of each head (64 of 256 dims)Rotates q and k by position so the dot product "knows" how far apart two tokens are

The catch: every new token has to look at every earlier token. The work per token grows with the context, and so does the memory, because every past k and v has to be kept.

Where k and v live: the paged KV cache

The k and v of past tokens are kept in GPU memory so they are not recomputed. That store is the KV cache.

vLLM does not give each request one long buffer. It cuts the cache into equal pages (also called blocks) of 1600 tokens (3,276,800 bytes, about 3.1 MiB per layer) and keeps a block table for each request. The table says which page holds which stretch of tokens. Pages can sit anywhere in memory, like pages of virtual memory in an OS, so requests can grow and shrink without fragmentation. Pages that start with the same prompt text can be shared between requests: this is prefix caching.

The odd size comes from the GDN layers, which share the same page pool. vLLM grows the attention page until it is at least as large as one GDN state page, which gives 1600 tokens (log: Setting attention block size to 1600 tokens). The llm-scaler image rounded this up to 2048 (chapter 1); upstream does not.

The KV cache is stored in FP8 (1 byte per number). The kernel converts it back to bf16 in registers as it reads it. The log says kv_cache_dtype=auto, but the checkpoint's kv_cache_scheme switches it to FP8. v0.30.0 still has that switch (vllm/model_executor/layers/attention/attention.py:285-286); chapter 1 has the details.

The other kind: GDN linear attention

48 of the 64 layers use Gated DeltaNet (GDN) instead. GDN still makes q, k and v, but it does not keep a list of past tokens. It keeps one fixed-size memory matrix S (128 × 128) per head and folds each token into it as it arrives:

  1. Forget a little. Multiply S by a decay α between 0 and 1. The model chooses α per token.

  2. Check what S already predicts for this key: S·k. Take the difference from the real value v. This is the "delta".

  3. Write the correction into S, scaled by a write strength β: S += β·(v − S·k)·kᵀ.

  4. Read out with the query: out = S·q.

Think of S as a small associative memory. Keys are addresses and values are contents. Writing the difference instead of adding v on top keeps old entries from piling up. Before these steps, q, k and v also pass through a short convolution over the last 4 tokens. That convolution's 3-token history is the conv_state, and it is the part that the chapter 3 bug corrupts.

The mix gets the best of both: GDN layers carry most of the long context cheaply, and every fourth layer can still look back precisely.

How the GPU runs work

A GPU is fast because it runs thousands of small threads at once. Intel's names for the levels (with the rough CUDA equivalent):

Figures from torch.xpu.get_device_properties(0) on this machine: gpu_subslice_count=32, gpu_eu_count=256, local_mem_size=128KB, sub_group_sizes=[16 32], total_memory=32656MB.

Why tiles. Doing the arithmetic is cheap. Fetching the numbers from VRAM is the slow part. A tile is a small rectangle of a matrix, sized to fit in registers or SLM. A kernel loads one tile, does as much arithmetic with it as it can, and only then loads the next. Each work-group owns some output tiles, and many work-groups run at once on different Xe cores. Choosing tile shapes is about keeping every Xe core busy without running out of registers or SLM.

How attention is tiled

Nobody builds the full table of scores (queries × every past key): at 21k tokens that would be 441 million numbers per head. FlashAttention instead walks through the keys one tile at a time and keeps a running result:

  1. Load a tile of queries into registers. It stays there for the whole walk.

  2. Load the next tile of k and v from the paged cache, using the block table to find the page.

  3. Compute the scores for this tile (Q·Kᵀ), update a running maximum and running sum for the softmax, rescale what has been added so far, and add this tile's weights·V.

  4. Repeat until the last key. Then divide by the running sum. The result equals ordinary softmax attention exactly; it is just computed in pieces (online softmax).

The FA2 kernels in vllm-xpu-kernels have two variants. The Python wrapper flash_attn_varlen_func (vllm_xpu_kernels/flash_attn_interface.py) picks one based on how many new tokens each request brings in this step:

Worked example: prefill of a 21k-token prompt

vLLM feeds the prompt in chunks of up to 4096 tokens (--max-num-batched-tokens=4096). One chunk gives 4096 / 256 = 16 query tiles × 24 heads = 384 work-groups per full-attention layer, which is plenty to fill 32 Xe cores. Each work-group walks the K/V tiles of its head from token 0 up to its own position, 32 keys at a time. Causal masking cuts the walk short.

Worked example: one token at 21k context

Take a single new token first. It shows why the decode kernel exists, and MTP verify builds on it. There is only one new token, so the query tile is tiny: 6 heads' worth of q. One work-group per KV head would be only 4 work-groups, which leaves 28 of 32 Xe cores idle. So the kernel also splits the keys (split-K). Worked example: an MTP verify step

With MTP 3, every generation step checks 4 tokens per request: the last accepted token plus 3 guesses. Sent as they are, those 4 query rows would go to the chunk-prefill kernel. That kernel's 256-row query tile would then be 4/256 full, and it has no split-K. The v0.30.0 kernel wrapper avoids this with a spec-decode fast path (vllm_xpu_kernels/flash_attn_interface.py:26-136, 510-537):

  • It applies when every request in the batch brings the same small number of tokens (2 to 16, VLLM_XPU_SPEC_DECODE_MAX_QLEN), the attention is causal, and the KV cache is paged.
  • Each (request, draft position) pair becomes its own one-token "decode row". Row j of a request sees only the keys up to its own position: seqused_k − (q_len − 1 − j). That is exactly the causal rule, with no mask needed.
  • All rows go to the split-K decode kernel in one launch, and the block table is repeated so every row finds its request's pages.
Verified in code

vLLM v0.30.0 meets every condition of the fast path on XPU. Attention is causal, there is no softcap or ALiBi, and q_descale is None because flash_attn_supports_quant_query_input() returns False on XPU (vllm/v1/attention/backends/fa_utils.py:311-312). The FP8 k_descale/v_descale are allowed.

Inference

The fast path needs a uniform batch. When one request is still processing its prompt while another is verifying, the query lengths differ and the batch takes the mixed path instead. There, the chunk-prefill kernel handles every request with more than 1 new token, including the verifying one (flash_api.cpp:247), and only 1-token rows go to the decode kernel. The same applies if more than one request is running and their draft counts differ. How often this happens with opencode traffic has not been measured.

How GDN is tiled

GDN has no history to walk. Its work is to update the 128×128 matrix S for each of the 48 value heads. The SYCL kernel _xpu_C.gdn_attention does this in two ways:

  • One token at a time (decode and MTP verify): a sub-group of 32 work-items owns a strip of 4 rows × 128 columns of S (v_dim_per_sg = 4, gated_delta_rule.hpp:7, 296-298; 8 sub-groups per 256-item work-group). Each head's S is split into 32 such strips. The strip stays in fp32 registers while the kernel loops over this step's tokens, and it is written back to the state cache afterwards (chapter 2).
  • In chunks of 64 tokens (prefill: chunk_gated_delta_rule_xe2, chunk_size_xe2 = 64 in csrc/xpu/gdn_attn/gdn_attn_utils.h:8). Updating S token by token would be a long sequential chain. The chunked form handles the 64 tokens inside a chunk together as small matrix multiplies, which suits the XMX units. Only S passes from one chunk to the next.

Processes and IPC

With TP=1 there are two Python processes. The API server sends requests to a spawned EngineCore process over ZMQ. The model worker is not a third process: UniProcExecutor runs it inside EngineCore and calls it directly.

  1. vllm serve with the default api_server_count runs the OpenAI server in the current process (vllm/entrypoints/cli/serve.py:145-148). It builds AsyncLLM with an AsyncMPClient (vllm/v1/engine/core_client.py:132), because VLLM_ENABLE_V1_MULTIPROCESSING defaults to 1 (vllm/envs.py:1335-1337).

  2. The client binds a ZMQ ROUTER for requests and a PULL for outputs on IPC paths (core_client.py:551-561). launch_core_engines then starts EngineCoreProc.run_engine_core through multiprocessing (vllm/v1/engine/utils.py:164-171).

  3. Inside EngineCore, a DEALER input thread and a PUSH output thread move msgpack messages between the sockets and in-process queues (vllm/v1/engine/core.py:1600-1603, 1707-1709). The busy loop (core.py:1358-1366) drains the input queue and calls step_fn.

  4. With world_size == 1 the executor is "uni" (vllm/config/parallel.py:927-928), i.e. UniProcExecutor. It constructs the worker, calls init_device and load_model in-process, then calls the platform block-size hook (vllm/v1/executor/uniproc_executor.py:46-69).

get_mp_context() uses VLLM_WORKER_MULTIPROC_METHOD. The generic default is fork (vllm/envs.py:921-923). XPU ends up with spawn in three ways: the image and compose both set it; XPUPlatform.check_and_update_config sets it when unset (vllm/platforms/xpu.py:328-329); and _maybe_force_spawn forces it once XPU is initialised (vllm/utils/system_utils.py:150-151).

The log shows Asynchronous scheduling is enabled. UniProcExecutor.supports_async_scheduling() is True (uniproc_executor.py:146-147), and MTP is an accepted method (vllm/config/vllm.py:1068-1116). With async scheduling the V1 runner gets max_concurrent_batches == 2 (vllm/config/vllm.py:516-521). EngineCore then uses a two-deep batch queue and step_with_batch_queue (core.py:199-205, 224-226): it schedules step N+1 while step N's outputs are still being processed.

Inference

With the uniproc executor, a "non-blocking" execute_model is still a direct Python call on the EngineCore thread (uniproc_executor.py:97-106). Overlap comes from asynchronous XPU kernel launches and asynchronous output copies, not from a second process. The XPU platform class

XPUPlatform (vllm/platforms/xpu.py, 505 lines) is where vLLM's CUDA assumptions are redirected to XPU. It chooses the attention backend, turns graph capture off, forces spawn, and adjusts the block size for GDN models. Importing the module also loads the SYCL kernel libraries and replaces a torch function process-wide.

A missing SYCL or Level Zero library therefore fails when the platform is imported, before any vLLM log line. All later "free memory" numbers come from the vllm-xpu-kernels op _C_cache_ops.getMemoryInfo. Torch's mem_get_info is used only when that op reports zero free bytes.

Block size for GDN models

For models with GDN layers, XPU rounds the KV block size up to a power of two. That is what turns the 1600-token block from the generic code into the 2048-token block seen in the log.

The live log shows the three stages in order:

Stage 1: FlashAttention on XPU prefers at least 64 tokens (flash_attn.py:93-97). Stage 2: _align_hybrid_block_size grows the block until one attention page (bytes per block per layer) is at least one GDN state page. It then pads the GDN page to match exactly (vllm/platforms/interface.py:884-946). Stage 3: the XPU override rounds 1600 up to 2048. The byte sizes are worked out in Hybrid KV and GDN state cache.

Memory budget and "Available KV cache memory"

The KV budget is 92% of total device memory minus weights, the activation peak of one dummy forward, and non-torch growth since the init snapshot. The code is the shared CUDA Worker.determine_available_memory. On XPU its only special case is that graph memory is never estimated.

requested_memory is ceil(total * gpu_memory_utilization). request_memory raises if the card has less than that free when the worker starts (vllm/v1/worker/utils.py:425-445). "Non-torch" memory is (total - free) - torch.accelerator.memory_reserved(), measured with the patched get_memory_info (vllm/utils/mem_utils.py:146-163, 306). It covers Level Zero and SYCL driver allocations, oneCCL buffers and kernel modules loaded during the profile run.

The live run fits the formula:

29.34 − 18.35 − 0.70 − 1.27 = 9.02 GiB. That matches the logged 9.01 GiB to rounding. The 0.7 GiB peak activation comes from one profile_run() forward at max_num_batched_tokens (4096).

Where it can break

Setting VLLM_XPU_ENABLE_XPU_GRAPH=1 allocates graph pools on top of this budget, because the estimate is gated on is_cuda_alike(). The project measured +2.5 GiB of unbudgeted memory with graphs on.

Model runner and the XPU custom ops

This model runs on the V1 XPUModelRunner, a thin subclass of the CUDA GPUModelRunner. Its constructor runs inside _torch_cuda_wrapper() and sets self.cascade_attn_enabled = False (xpu_model_runner.py:16-28). The wrapper permanently rebinds torch.cuda stream and event APIs to their XPU equivalents.

Hybrid KV and GDN state cache ('align' mode)

Full-attention KV blocks and GDN state blocks come from one pool of equal-size 4 MiB pages. Each request holds up to 64 attention blocks per full-attention layer group. In each of 3 GDN groups it holds a small window of state blocks: 2 plus the number of speculative tokens. With prefix caching on, Qwen3.5 must use mamba cache mode align.

Why 'align'

Qwen3_5ForConditionalGeneration(Qwen3VLForConditionalGeneration, IsHybrid) (vllm/model_executor/models/qwen3_5.py:400) does not mix in SupportsMambaPrefixCaching, so the mode becomes align. qwen3_5.py:308-312 also raises on all. The modes are defined as follows:

In align mode the scheduler clips prefill chunks to end on block boundaries (vllm/v1/core/sched/scheduler.py:355-405). Each request keeps a small rolling window of state blocks. MambaManager frees the block from two steps ago and replaces it with a null block (vllm/v1/core/single_type_kv_cache_manager.py:1395-1413).

num_speculative_blocks equals num_speculative_tokens (vllm/model_executor/layers/mamba/abstract.py:56-60). With MTP=3, each GDN layer reserves 5 state pages per request. The extra 3 are the per-draft-token slots that speculative GDN decode writes into (chapter 3).

How the pool is split

Layers are grouped by spec. The group size is the smallest per-type layer count (kv_cache_utils.py:1203-1216). Each of the group_size raw int8 tensors (allocated at gpu_model_runner.py:7313-7315) is shared by one layer from every group. Each layer's block table decides which pages of the shared tensor it uses. For this run:

  1. Full-attention layers: 16 in the main model plus 1 in the MTP head, 17 in total (inference). GDN layers: 48. The log line Add 3 padding layers, may waste at most 6.25% KV cache memory is consistent with a group size of 17: the 48 GDN layers split into 3 groups of 17, which needs 3 padding layers, and 3/48 = 6.25%.

  2. That gives 17 shared tensors, each 4 MiB × num_blocks. One block across all of them is 17 × 4 MiB = 68 MiB. 9.01 GiB / 68 MiB gives 135 blocks (get_num_blocks, 990-1007).

  3. Per request (kv_cache_utils.py:937-955): the attention group needs cdiv(131072, 2048) = 64 pages. Each GDN group needs 2 + 3 = 5, so 15 for three groups. The total is 79 blocks.

  4. Concurrency = 135 / 79 = 1.709 and tokens = int(1.709 × 131072) = 223,983. This matches the logged GPU KV cache size: 223,983 tokens and Maximum concurrency ... 1.71x.

Sampling

By default, top-k/top-p sampling runs through a fused SYCL kernel. The fallback warning in the startup log is produced by the engine's own warmup, not by user requests.

VLLM_XPU_USE_SAMPLER_KERNEL defaults to 1 (envs.py:2006-2008). The warning [topk_topp_sampler.py:293] ... Falling back to PyTorch-native implementation appears at 07:10:06 in the log, before Available KV cache memory, i.e. during profile_run. The dummy sampler run deliberately calls the sampler a second time with a seeded generator to warm the native path:

  • At runtime, any batch that contains a request with its own seed takes the native path. Because the warning is warning_once and was already used by the warmup, this happens silently.
  • The native path uses the Triton top-k/top-p kernel only when the batch has at least 8 rows. Otherwise it sorts the whole vocabulary in PyTorch (topk_topp_sampler.py:354-360). With --max-num-seqs=4 it always sorts.
  • With MTP, draft tokens are verified by the rejection sampler. The log shows rejection_greedy_sample_kernel being JIT-compiled at the first request.
Verified in code

Model layout and quantization

Three of every four decoder layers are GDN linear-attention layers. That makes 48 GDN layers and 16 full-attention layers out of 64. All GDN layers stay in bf16, because the checkpoint's quantization ignore list names them. A GDN (Gated DeltaNet) layer replaces softmax attention with a fixed-size recurrent state per sequence, updated once per token. Its per-request state is therefore a constant-size "mamba-style" cache entry, not a growing KV cache.

The gated delta rule as implemented

Each GDN layer keeps, per sequence and per v-head, a V×K matrix S that is decayed, corrected toward the new key/value pair, and read out with the query at every token. The reference Triton kernel used for decode and spec verify on CUDA defines the arithmetic:

Written out for one sequence, v-head h (using k-head h div 3) and token t:

  1. Project. [q|k|v|z] = Wqkvz xt and [b|a] = Wba xt.

  2. Causal conv. The conv is width 4 and depthwise over the 10240 q/k/v channels: ct = silu( Σi=0..3 wi · ut-3+i + bias ). The previous three inputs ut-3, ut-2, ut-1 come from conv_state. z skips the conv.

  3. Gates. gt = −exp(A_logh) · softplus(at,h + dt_biash), αt = exp(gt), βt = sigmoid(bt,h).

  4. Normalize. q̂ = q / sqrt(‖q‖2 + 10-6) · K-1/2 and k̂ = k / sqrt(‖k‖2 + 10-6).

  5. Delta rule. In order: S ← αt S; δ = βt (vt − S k̂); S ← S + δ k̂T; ot = S q̂.

  6. Gate and project out. Apply an RMS norm per head over V, then multiply by silu(z): yt = RMSNorm(ot) · wnorm ⊙ silu(zt). Finally out = Wout yt (RMSNormGated with norm_before_gate=True, layernorm.py:273-318).

Because S accumulates every δ k̂T outer product, a single wrong k or v keeps affecting later outputs until the decay α washes it out. A conv-window error of only three tokens can therefore leave a lasting error in the state.

Where it can break

Because of the exact-count check, a spec request with fewer drafts than num_speculative_tokens makes the op throw rather than compute. That would appear as an engine error, not as corrupted text. Upstream relaxed the check in vllm-xpu-kernels PR #600. The vLLM builder sizes spec_token_indx as min(num_spec_decodes*(num_spec+1), total) (gdn_attn.py:299-302).

For non-spec tokens, prefills on XE2 go through chunk_causal_conv1d[_tiled]_xe2 + chunk_gated_delta_rule_xe2 (gdn_attn_interface.cpp:410-518). The two conv-state layouts

There are two incompatible conventions for where the conv window lives during speculative decoding. vLLM's CUDA/Triton kernels and its block-copy code use a sliding window in column 0. The XPU spec conv kernel in this image uses token-indexed snapshots, one per spec column. The SSM state uses per-column checkpoints in both.

Layout A: sliding window in column 0 (vLLM contract, CUDA/Triton)

Only slot spec_state_indices[n, 0] holds conv state. All 3 + num_spec rows are used.

  • Before the step, the rows hold history.
  • After the step, the rows are [histo+1, histo+2, x0, x1, …, xnum_spec], where o = num_accepted−1 from the previous step.
  • On the next step, the kernel reads 3 rows starting at row offset num_accepted−1. That offset selects the window that ends at the last accepted token.

vLLM's align-mode block copy is written for layout A. When a request's running block changes, the conv state is copied from the column-0 block starting at row num_accepted−1. The SSM state is copied from column num_accepted−1. The fused Triton postprocess kernel follows the same rule (vllm/v1/worker/mamba_utils.py:108-125).

Layout B: token-indexed per spec column (XPU SYCL kernel at a692986)

After verify token t, the kernel writes the 3-row window [ut-2, ut-1, ut] into rows 0..2 of slot spec_state_indices[n, t]. On the next step it reads rows 0..2 of slot spec_state_indices[n, num_accepted−1]. Rows 3..5 of every slot are never written by any XPU conv kernel. The spec kernel, the non-spec kernel (causal_conv1d.hpp:309) and the XE2 prefill kernels all write Width−1 rows. Width is taken from conv_weights.size(1) (causal_conv1d.hpp:1038).

The header comment of this kernel (causal_conv1d.hpp:476-497) claims it writes "ONLY the last cache slot ... matching the Triton fused_recurrent path". The code does not do that.

Layout B is self-consistent while the 4 slot columns stay fixed. In align mode they move every 2048 tokens, and the copy then applies the layout-A rule to layout-B data. For example, with num_accepted = 3, the next step reads column-0 rows 2..4. Under layout B those rows are [u0, junk, junk]. The correct window is [u0, u1, u2], which sits in rows 0..2 of column 2.

Where this layer can break

The primary suspect is the conv-layout mismatch, covered in chapter 3. The code in this layer has two further, weaker suspects and two hazards that only apply to other configurations.

Where it can break

Primary: conv-state layout mismatch (layouts above, deep dive in chapter 3). The code is consistent with MTP-only corruption: with MTP off, num_accepted is always 1, and the copy is correct in both layouts (inference).

Secondary: NULL_BLOCK_ID = 0 versus pad slot -1

MTP speculative decoding and the conv-state bug

This chapter follows one speculative-decoding step through the scheduler, the target verify pass, the rejection sampler and the MTP proposer. It then shows how the GDN recurrent state is rolled back and copied, and why a disagreement over the conv-state layout corrupts long generations only when MTP is on.

All vLLM paths below are relative to /opt/venv/lib/python3.12/site-packages inside intel/llm-scaler-vllm:0.26.0-b2 (vLLM 0.26.1.dev0+g568afb3a1). Native kernel sources come from the copy that ships in the same image at /llm-scaler/vllm/vllm-xpu-kernels. That is vllm-xpu-kernels 0.1.11.2.dev0+ga692986, i.e. tag v0.1.11.1 plus Intel's llm-scaler patch. The deployment runs in bf16 with a 2048-token attention/mamba block size (chapter 1).

Configuration and the MTP draft layer

--speculative-config={"method":"mtp","num_speculative_tokens":3} reuses the target checkpoint as the draft model and renames its architecture to Qwen3_5MTP. That class is one full-attention decoder layer that reuses the target's embeddings and lm_head.

The draft module builds mtp_num_hidden_layers decoder layers (one in this checkpoint), all of type full_attention. Its forward concatenates the normalized embedding of token t+1 with the normalized target hidden state at t, projects the result back to hidden size with fc, and runs the attention layer.

Verified in code

The MTP layer has no GDN sublayer and no mamba state. layer_type="full_attention" makes Qwen3_5DecoderLayer build a Qwen3NextAttention (qwen3_5.py:145-153). Its KV cache joins the target's full-attention KV group; the startup log's "Add 3 padding layers, may waste at most 6.25%" is consistent with 17 attention layers (16 target plus 1 MTP) against 48 GDN layers. Embeddings and lm_head are shared unconditionally for MTP (v1/spec_decode/llm_base_proposer.py:1495-1501, 1571-1582). Qwen3_5MTP.__init__ rejects mamba_cache_mode == "all" (qwen3_5_mtp.py:216-220). With prefix caching enabled, align is therefore the only mode MTP can run under.

The startup warning "Enabling num_speculative_tokens > 1 will run multiple times of forward on same MTP layer" (speculative.py:895-909) means the proposer calls this one layer three times in sequence, feeding back its own hidden state and the token it just drafted. The layer was trained to predict one token ahead, so drafts 2 and 3 are accepted less often. The warning is about acceptance rate, not correctness.

Two settings decide which code paths run. Hybrid models use the V1 runner: use_v2_model_runner returns False when model_config.is_hybrid (vllm/config/vllm.py:622-623), so XPUModelRunner subclasses v1/worker/gpu_model_runner.py (v1/worker/xpu_model_runner.py:16-27). The drafter batch is padded, because disable_padded_drafter_batch defaults to False (speculative.py:139).

One engine step with spec decode

Each step verifies the previous step's drafts with one target forward pass. It then drafts k=3 new tokens with the MTP layer. Under async scheduling the scheduler only ever sees placeholder drafts.

  1. Schedule (v1/core/sched/scheduler.py:502-518, 622-638). A decoding request gets num_new_tokens = 1 + k: the last sampled (bonus) token plus the drafts. Blocks for k lookahead positions are allocated too (:564-568). With async scheduling the drafts are -1 placeholders (v1/core/sched/async_scheduler.py:16-44), and num_computed_tokens advances optimistically by 1+k (scheduler.py:1246-1250).

  2. Prepare inputs (gpu_model_runner.py:1971-2293). Positions, seq_lens and the slot mapping are built from num_computed_tokens, which is corrected on the GPU from the previous step's valid-token count (:2163-2212). The real draft ids are scattered from the GPU into input_ids (:1896-1924). num_decode_draft_tokens[i] = draft_len is set only when num_scheduled == draft_len + 1 (:2257-2278). This array is what marks a request as a spec decode for GDN.

  3. Align-mode preprocess (:4299-4340). preprocess_mamba copies GDN state when the running 2048-token block changes, then re-syncs num_accepted_tokens to the GPU. Details are in Align-mode prefix caching copies.

  4. Verify forward (:4422-4478). The target runs over [bonus, d1, d2, d3] for each decoding request, plus any prefill chunks, and produces logits at all 1+k positions (_calc_spec_decode_metadata, :2855-2928).

  5. Rejection sample (v1/sample/rejection_sampler.py:429-471, 745-771). At temperature 0 each draft is kept while it equals the target argmax. The first mismatch is replaced by the target token, the rest become -1, and the bonus token is appended if every draft was kept.

  6. Count and postprocess (gpu_model_runner.py:1590-1618). num_accepted_tokens = (output_token_ids != -1).sum(dim=1) gives a value from 1 to k+1. Then the fused kernel postprocess_mamba_fused_kernel saves the block-aligned state for prefix caching.

  7. Prepare the drafter (:5179-5251). eagle_prepare_next_token_padded_kernel picks the last accepted token. eagle_prepare_inputs_padded_kernel computes token_indices_to_sample = q_last - num_rejected (v1/spec_decode/utils.py:136-238).

  8. Propose (llm_base_proposer.py:507-790). Pass 1 runs the MTP layer over every token the target just processed, with the input ids shifted by one and the target's own positions and slots (:861-883). Passes 2 and 3 each process one token per request. eagle_step_slot_mapping_metadata_kernel advances the position by one and computes the slot from the 64-token kernel block table (utils.py:28-85).

  9. Roll back on the scheduler (scheduler.py:1680-1699). num_computed_tokens -= num_rejected. KV and mamba blocks are not rolled back. Attention KV for rejected positions is overwritten later, and GDN state is rolled back through slots, described next.

Verified in code

At temperature 0 every emitted token is the target model's argmax at a verified position. A bad draft can only lower the acceptance rate. For MTP to change the text, the target forward must itself be wrong: the target's state after a spec step has to differ from what plain one-token decode would produce. For the hybrid model that points at the GDN state.

GDN state under spec decode

With spec decode, each request gets k+1 GDN state slots, one per verified token. The next step starts from the slot of the last accepted token, num_accepted_tokens - 1.

A GDN layer carries two states (chapter 2). The conv state is the last conv_kernel - 1 = 3 inputs of a short causal convolution. The SSM (temporal) state is a [H_v, D_v, D_k] matrix. With spec decode the conv block is allocated with room for k extra rows:

Each conv block therefore has 6 rows (3 + 3) of conv_dim values in the default "SD" layout (mamba_utils.py:43). The slot block ids come from the mamba block table. In align mode, the builder gathers the 1 + k columns that start at the block holding the last scheduled token:

Its SSM spec kernel reads slot a-1 and writes every slot:

For the SSM state this matches upstream Triton (fused_sigmoid_gating_delta_rule_update(..., ssm_state_indices=spec_state_indices_tensor, num_accepted_tokens=...), qwen_gdn_linear_attn.py:1459-1477). Where it can break

Because the non-spec path reads column 0 and ignores num_accepted_tokens (gdn_attn.py:256-268), a request that accepted a>1 tokens must either be scheduled as a spec decode again, or have its state copied into column 0. The copy happens in align mode, below.

Align-mode prefix caching copies

With --enable-prefix-caching, GDN state is kept in 2048-token "align" blocks. The runner copies state between blocks in two places: before the forward pass when the running block changes, and after sampling when an accepted run crosses a block boundary.

Both copies use the model's state-copy functions. For Qwen3.5 those are (get_conv_copy_spec, get_temporal_copy_spec) (qwen3_5.py:565-566, mamba_utils.py:352-353). The two functions disagree on where the accepted count applies. The temporal copy picks the source block src + a - 1. The conv copy stays on block src and skips a - 1 rows:

Pre-forward copy. preprocess_mamba runs on the CPU every step. When the running column moves from prev_state_idx to curr_state_idx, it queues the copies with the previous step's accepted count and resets that count to 1. The copies run in batch_memcpy_kernel (v1/worker/mamba_utils.py:408-434).

The runner then re-syncs the reset count to the GPU, so the GDN kernel reads slot 0 of the new block (gpu_model_runner.py:4318-4325).

Post-sampling copy. postprocess_mamba_fused_kernel (Triton) checks whether the accepted run crossed a 2048 boundary. If so, it saves the state at that boundary into the block that ends there, which becomes the prefix-cache snapshot. When source and destination are the same block, it also resets the accepted count to 1. Its shared copy body applies the same row-offset rule to conv states:

On the scheduler side, the decode spec slots roll forward. When the running column advances from s to s+1, nothing is moved: the old spec block at s+1 becomes the running block, and one new block is appended (v1/core/single_type_kv_cache_manager.py:1522-1567). Skipped mamba blocks are freed only after the processed, non-optimistic token count passes them (v1/core/kv_cache_manager.py:440-447). Mamba blocks are not zeroed on allocation. The conv-state layout bug

The XPU GDN spec kernel stores a separate 3-row conv window per slot. vLLM's align copies assume the upstream layout: one 6-row sliding window in slot 0. So when a request crosses a 2048-token block boundary with more than one accepted token, the conv window copied into the new block is partly built from rows no XPU kernel ever wrote.

Side 1: the XPU SYCL kernel keeps one conv window per slot

With Width = 4 the kernel only ever reads or writes rows 0..2 of a conv block. The non-spec (prefill and decode) path does the same (causal_conv1d.hpp:257-264 reads, :321-324 writes). The kernel's own reference test encodes this layout: init_slot = spec_state_indices_tensor[n, naccepted-1], then conv_state[slot] = qkv_conv_input[t + 1:t + width] for each t (tests/gdn_attn/test_gdn_attn.py:591-603 in the same tree). Rows 3..5 of every 6-row conv block are never written by any XPU GDN kernel.

Side 2: vLLM (and upstream Triton) keep one sliding window with a row offset

The upstream GDN path passes conv_state_indices=spec_state_indices_tensor[:, 0] together with num_accepted_tokens (qwen_gdn_linear_attn.py:1347-1360). That is the layout get_conv_copy_spec and _copy_mamba_state_block assume. On XPU this path is not used.

Worked example: crossing 20,480 with num_accepted = 3

Block size B = 2048, and 20,480 = 10 × 2048. Take a request with k = 3 whose target has already processed 20,475 tokens.

  1. Step N-1 schedules 4 tokens at positions 20475..20478, so seq_len = 20479 and s = 20478 // 2048 = 9. The slots are bt[9], bt[10], bt[11], bt[12]. The XPU kernel writes rows 0..2 of each slot: bt[9] gets the window after position 20475, which is [x20473, x20474, x20475]. bt[10] gets the window after 20476, and bt[11] gets the window after 20477, [x20475, x20476, x20477].
  2. Two drafts are accepted and the third is replaced by the target's own token, so num_accepted = 3 and num_computed becomes 20478. The postprocess kernel sees aligned_new_computed = 18432, which is below the running count of 20476, so it copies nothing.
  3. Step N schedules 4 tokens: seq_len = 20482, and curr_state_idx = cdiv(20482, 2048) - 1 = 10, which differs from prev_state_idx = 9. preprocess_mamba queues copies with num_accepted = 3:
    • SSM: bt[9 + 3 - 1] = bt[11] to bt[10]. This is correct: it is the state after position 20477.
    • Conv: rows 2..5 of bt[9] to rows 0..3 of bt[10]. The new rows 0..2 are [x20475, stale, stale]. The kernel needs [x20475, x20476, x20477], rows 0..2 of bt[11].
  4. The count is reset to 1, so step N's spec kernel reads rows 0..2 of bt[10] as the conv history. The convolution outputs for the next three tokens mix in two stale vectors. Those q/k/v values are folded permanently into the SSM state of all 48 GDN layers.

Upstream fix: PR #544 and #545

Upstream fixed this in the kernel. vllm-xpu-kernels PR #544 ("[GDN] Fix token-indexed conv-state layout in causal_conv1d spec-decode kernel", merged 2026-08-25 as 5802a41) switches the spec conv kernel to the single-line sliding window that vLLM's copies expect. PR #545 (02f65ce) fixes the state length it uses. Both shipped in v0.1.14; the image's 0.1.11.x build contains neither.

The PR description names the same root cause: the kernel "writes conv state token-indexed (a full snapshot per speculative token, one per block-table column), but vLLM's generic Mamba copy (get_conv_copy_spec) expects a single sliding-window cache line read by row offset. When num_accepted_tokens > 1 at a cache-block boundary, the wrong conv state migrates into the next block". It credits the diagnosis to vllm-project/vllm#53229 and dates the token-indexed layout to vllm-xpu-kernels#368.

PR #545 corrects how that state length is derived. A first version computed it from the leading stride, conv_states_stride_0 / conv_elems. That is wrong for vLLM's per-layer views of a shared allocation: the PR measured stride 589824 against shape (3067, 6, 6144), which gives 96 instead of 6. The kernel now uses Width - 1 + (num_spec_tokens - 1), which is 6 here because num_spec_tokens is the slot-row width 4. gdn_attn_interface.cpp gained a TORCH_CHECK(conv_state.size(1) >= required_conv_state_len). The fix is kernel-only: the SSM path keeps one slot per token, matching get_temporal_copy_spec, and vLLM itself is unchanged. The PR's end-to-end check (Qwen3.5-0.8B, MTP k=3, bf16) diverged right after a cache-block boundary before the fix and matched the no-boundary control token for token after it.

Inference

The ESIMD fp16 spec kernel in custom-esimd-kernels-vllm already supports the packed single-line layout whenever conv_state_len >= num_spec_tokens + 2 (csrc/xpu/esimd_kernels/gdn_conv_fused_seq_spec.h:203-213). It is only used for fp16 batches with exactly one spec request (_xpu_esimd.py:1006-1015). With --dtype float16 and several concurrent requests, one request could alternate between ESIMD (packed) and SYCL (per-slot) steps and read a mismatched window. Switching this deployment to fp16 is therefore not a workaround.

Kernels, runtime and driver

This chapter covers every layer between a torch.ops._xpu_C.gdn_attention call and the Battlemage silicon: what each layer does, who owns it, which version is in intel/llm-scaler-vllm:0.26.0-b2, and how that was checked. For the MTP bug, it separates what a runtime upgrade can change (driver scheduling, copies, just-in-time compiled code) from what it cannot: the GDN kernels are compiled ahead of time, so a new runtime does not recompile them.

PyTorch XPU, oneDNN and Triton

PyTorch gives vLLM the device, streams, allocator and generic operators. Triton compiles vLLM's Python-level kernels and every torch.compile kernel into SPIR-V (the Khronos portable GPU intermediate language), which Intel's graphics compiler then turns into native code.

torch.xpu maps each PyTorch stream to a SYCL queue (SYCL is the Khronos C++ single-source GPU programming model that Intel's oneAPI implements). Collectives use the xccl backend, which sits on oneCCL.

Triton XPU backend

Triton lowers ttir → ttgir → llir → spv and can optionally add a zebin stage (Intel's native GPU ELF binary). Which path runs depends on the caller.

  • Plain Triton (for example vLLM's FLA helper kernels): generate_native_code defaults to False.   • Inductor (torch.compile): torch/_inductor/runtime/triton_heuristics.py:843-844 sets generate_native_code=True when XPU_KERNEL_FORMAT == "zebin". Triton then runs ocloc compile -file x.spv -spirv_input -device <arch> (compiler.py:489-495) and caches the zebin.

vllm-xpu-kernels, the llm-scaler patch, and ESIMD kernels

The GDN kernels that run during MTP verification in this image are the SYCL kernels in vllm-xpu-kernels v0.1.11.1, modified by Intel's downstream llm-scaler patch. They do not include the upstream conv-state fix (PRs #544 and #545, released in v0.1.14; see the conv-state bug).

vllm-xpu-kernels (vllm-project/vllm-xpu-kernels) is vLLM's native XPU operator library, written in SYCL C++, with SYCL-TLA (CUTLASS for SYCL) for the Xe2 attention, GEMM and GDN chunk kernels. It builds four extension modules (CMakeLists.txt:529-691):

Host dispatch of gdn_attention

The spec tokens and the non-spec tokens of a step are processed in one call. The spec path runs first, on the same SYCL queue, which is the current torch XPU stream (csrc/utils.h:38-42).

The spec recurrent kernel reads one saved state per request and writes one state per processed token. The next step reads the column that matches how many draft tokens were accepted.

Where it can break

vLLM pads unused spec rows with NULL_BLOCK_ID = 0 (vllm/v1/attention/backends/utils.py:46, gdn_attn.py:477). The Triton reference kernel skips such slots with if state_idx <= 0: return (vllm/third_party/flash_linear_attention/ops/fused_recurrent.py:113-115). The SYCL spec recurrent kernel has no slot check. The spec conv kernel checks only != pad_slot_id, and pad_slot_id is −1 (gdn_attn_interface.cpp:279; causal_conv1d.hpp:720,817). Upstream main @68d82174 is the same. The host also never validates index values, only shapes and dtypes. (Inference) If a live request's row ever contains block 0, the SYCL kernels would read and write the shared null slot, where Triton would skip it.

ESIMD kernels from llm-scaler

ESIMD ("Explicit SIMD", sycl::ext::intel::esimd) is a DPC++ extension with "APIs close to the Intel GPU ISA" and a simd class "mapped to Intel GPU's general register file" (extension spec). In plain SYCL, each work item handles one lane and the compiler vectorizes the code. In ESIMD, the programmer writes explicitly vectorized code instead.

custom_esimd_kernels_vllm 0.1.0 ships 10 extension modules. Its ops include esimd_gdn_conv_fused_seq_spec (csrc/xpu/torch_extension_lgrf.cc:34-44). The patched vLLM tries ESIMD first and falls back to _xpu_C.gdn_attention.

Verified in code

Qwen3.8-27B has linear_num_key_heads=16 and linear_num_value_heads=48 (model config.json) and runs at TP=1, so the ESIMD spec path never qualifies. The ESIMD decode-only path also requires fp16 tensors (_xpu_esimd.py:750-758), and this model runs in bf16. Every GDN call in this deployment uses the SYCL _xpu_C.gdn_attention kernels shown above. The env switch DISABLE_ESIMD_GDN_SPEC=1 (:17) exists but changes nothing here.

SYCL runtime, Unified Runtime, Level Zero, IGC and gmmlib

Between PyTorch and the kernel driver, four Intel libraries turn a SYCL kernel submission into GPU commands, and a fifth compiler library produces the machine code. On this Xe2 GPU the path uses the newer "V2" Level Zero adapter, which by default moves copies onto the dedicated copy engine (BCS).

xe kernel driver, GuC, firmware, hardware, and the page fault

The xe driver submits all GPU work through the GuC firmware scheduler. The single fault this host logged was a copy-engine read into an address space that had already been torn down while docker stopped a container. By itself it is not evidence of a kernel memory bug.

Engines and limits on this host

  • Found battlemage (device ID e223) … stepping C0, Running in SR-IOV PF mode, 32 GiB VRAM (journalctl -k).
  • GT0: ccs1/ccs2/ccs3 fused off, so there is one compute engine (CCS, ccs0), plus one copy engine class (BCS) and one render engine (RCS). The sysfs directory /sys/class/drm/card1/device/tile0/gt0/engines/ lists bcs ccs rcs.
  • job_timeout_ms is 5000 for ccs and bcs. A job running longer than that goes through the timeout path, which prints "Timedout job" (xe_guc_submit.c:1609 @v7.2).
  • An execution queue "is associated with a specified HW engine … tied to an address space (VM)" (xe_exec_queue.c:34-54 DOC).

The logged fault

In the system journal, dockerd sent SIGTERM to container 733d08c1… at 23:59:57 and force-killed it at 00:00:07 ("failed to exit within 10s of signal 15"). That container had run for 50 minutes with an 8.3 GB memory peak. The fault falls inside that window.

  • -ENOENT means the process's GPU address space (VM) was already closed when the fault was handled. A wild pointer inside a live process would show -EINVAL. xe_pagefault_queue_work prints the block plus "Fault response: Unsuccessful %pe" (xe_pagefault.c:308-314).
  • "log buffer overflow" is printed only by xe_guc_check_log_buf_overflow() (xe_guc_log.c:660-679). Its only caller is the GuC state-capture handler (xe_guc_capture.c:1409), which runs after GuC captures engine registers for an error or reset. It means GuC's error-capture buffer wrapped. It does not mean the kernel log overflowed.
  • The reset handler prints "Engine reset" only if (!exec_queue_killed(q)) (xe_guc_submit.c:2948-2951), so resets of a killed queue are silent.
Inference

A copy on the copy engine was still queued or running when the dying process's VM closed. GuC captured state for that context, silently because the queue was killed, and the late fault was answered with -ENOENT. vllm#55425 shows the same engine and errno at Faulted Address: 0x0000d556aa4c7000, 64 KiB from this host's …aa4b7000, after a CCS timeout. A near-identical address across machines points to a buffer that the runtime (NEO or UR) allocates internally and copies on BCS near teardown. UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1 is the cheap A/B.

devcoredump. After a hang, the snapshot is at /sys/class/drm/card1/device/devcoredump/data. Only the first failure is kept, until userspace writes to the file or a one-hour timer (XE_COREDUMP_TIMEOUT_JIFFIES (60 * 60 * HZ)) releases it (xe_devcoredump.c:30-66). Confirm it on this machine

Two experiments confirmed it. The first takes the block copies out; the second shows the damage starting at a block boundary. They can be re-run on any future image.

  1. Prefix caching off, MTP on. Mamba cache mode becomes none, so no conv state is ever copied between blocks. Expect 0 corrupted rounds in 40. Any corruption here would point away from this bug.

  2. Long greedy output, MTP on vs off. Use a short prompt, temperature 0 and max_tokens around 4000, with prefix caching on. The two outputs should be identical, or nearly so, until close to 2048 total tokens (prompt plus output), then diverge. Record the token index where they first differ.

  3. Optional: log the copies. Add a log line in preprocess_mamba with request id, token count, old and new block, and num_accepted_tokens, and match the positions against where garbage starts. Chapter 3 lists the exact lines.

Experiment 1: 0 of 40 rounds corrupted. Experiment 2: MTP output first differs from MTP-off at sequence positions 2051 and 2082, then one run collapses into ':':':'…. Both results match the prediction. Experiment 3 was not needed.

Where it can break

Two hazards remain after the main fix. First, with XPU graphs on, vLLM pads unused state slots with block id 0, which the Triton reference skips but the SYCL kernels don't (ch. 2). It is inactive with graphs off, as here, but matters if you later enable VLLM_XPU_ENABLE_XPU_GRAPH together with MTP. Second, the Level Zero v2 adapter offloads copies to the copy engine; UR_L0_V2_FORCE_DISABLE_COPY_OFFLOAD=1 is a cheap A/B (ch. 4). Re-test with a separate cache volume, because compiled kernels in the shared vllm-cache volume can carry over between configurations.
